# Remote access through a Tailscale route to the NAS's private address

The household's own devices reach RememberWhen from outside the house through **Tailscale**, with the NAS advertising a `/32` subnet route to **its own LAN address**. A remote device resolves `nas.vandehaar.dev` through public DNS to the private address exactly as [ADR 0003](0003-public-dns-pointing-at-a-private-address.md) designed, and the packet goes into the tunnel instead of nowhere. The origin does not change, so the certificate, the authorization threshold of [ADR 0004](0004-the-app-is-served-from-the-nas-so-the-media-is-same-site.md), the Service Worker scope and the installed app are all the same object at home and away. That is the point of the design: the login is solved once, for both.

It looks odd without context: a VPN whose only route leads back to the machine running it. It is deliberate. Any route that gave the NAS a *different* name — a Tailscale `100.x` address, a tunnel hostname, a QuickConnect name — would be a different origin, and ADR 0004 already established that the credential only survives Safari's `<img>` and `<video>` same-site.

The owner's "no public internet exposure" line was sharpened for this decision to what ADR 0003 actually said: **no inbound port**. Encrypted point-to-point transit over the internet is acceptable. Tailscale is outbound-only and indifferent to the house's double NAT, relaying through DERP when no direct path exists. Full findings: [`docs/research/remote-access-on-a-ds120j.md`](../research/remote-access-on-a-ds120j.md), decided in [issue #53](https://github.com/marcovandehaar/rememberwhen/issues/53).

## Considered options

- **Cloudflare Tunnel, private-network form** (`cloudflared` on the NAS plus the Cloudflare One client on each device). Also preserves the origin, for the same reason. Runner-up and the named **fallback** if the device test below fails. Not first choice: a community package on this model, every byte hairpins through Cloudflare's edge even for a device one room away, and it drags in a Zero Trust organisation with enrolment policies and split-tunnel configuration — architecture for a six-device household.
- **Cloudflare Tunnel, public-hostname form** — the one most tutorials describe. A different origin, and it puts the authorization threshold on the open internet, which ADR 0004 says would not be proportionate. Gating it with Cloudflare Access means an interactive login, which the kids cannot do.
- **Synology VPN Server, WireGuard.** Servers that wait for connections: an inbound port, forwarded through both NAT layers. Out on the principle alone. VPN Server has no WireGuard, and the community WireGuard package never supported this platform.
- **ZeroTier, Headscale, QuickConnect, Tailscale Funnel.** A container runtime on a 512 MB box; a public coordination server the household does not have; a different, public origin; public exposure by design.

## Consequences

- **The whole design rests on one untested behaviour**: that a Tailscale userspace subnet router on DSM 7 forwards to its own LAN address. Nobody documents it either way. The first build step is to test it — an iPad on cellular opening the app, with `<img>`, `<video>` range requests and the catalogue fetch watched — and this ADR is to be amended with the result, as ADR 0004 was. If it fails, the fallback is the Cloudflare private network, not a different name.
- **One tailnet, owned by Marco, signed in with Apple.** Every device — the kids' iPads, Marco's iPhone, the Android phone, the work laptop — joins under that one account. Nobody else needs an account. Enrolment stays per device, the shape ADR 0004 already had.
- **Kids do nothing.** iPads and the iPhone use VPN On Demand: connect on every network **except** the home Wi-Fi, always on cellular. The Android phone uses the OS's Always-on VPN. The work laptop is toggled by hand, because it also runs the employer's VPN and never needs both at once.
- **At home the app does not depend on Tailscale.** The On Demand rule keeps the VPN off on the home Wi-Fi, and iOS routes traffic for the directly-connected subnet out of the Wi-Fi interface even when a VPN is up. A Tailscale outage cannot break the app at home on iOS. Android at home is untested.
- **The overlap trap is known and deliberately left open.** iOS will not send traffic through any VPN to an address inside the subnet of the Wi-Fi it is on. On a foreign network using the same range as the home LAN — and the consumer defaults are what most homes run — remote access fails. The fix is to renumber the home LAN to an uncommon range and update ADR 0003's A record once. The owner chose to **postpone** that until the device test has reproduced the failure on a same-range network; renumber only if it bites.
- **Node key expiry is disabled on every device.** Tailscale's default is 180 days, after which the device silently loses remote access until someone re-authenticates. This belongs in the one-time setup, together with the NAS itself.
- **A split-DNS entry sends `vandehaar.dev` to a public resolver over the tailnet.** Resolvers with DNS-rebinding protection drop public answers containing private addresses; ADR 0003 never met them because the name was only used at home. The On Demand rule keeps this off at home.
- **Peer Relay and `tailscale serve` stay off on the NAS.** Both have reports of memory or CPU cost on small devices. `tailscaled`'s memory on the DS120j is unmeasured and is part of the device test, against the ~186 MB free.
- **Losing a device is two removals**: the machine in Tailscale's admin console, and its credential on the NAS.
- **Remote throughput is the home uplink's, not a design choice.** Userspace WireGuard on an 800 MHz A3720, direct or via DERP, is unmeasured; whether a 20 MB clip is watchable away from home is part of the test, not a reason to wait.

## Amendment, 2026-09-30: the bet holds

The one untested behaviour this ADR rested on was measured, on the household's own devices ([issue #56](https://github.com/marcovandehaar/rememberwhen/issues/56)). The NAS does forward traffic to its own LAN address as a userspace subnet router, so **the Cloudflare fallback is not needed**.

- **Setup that was used:** the Synology Package Center's Tailscale package (1.58.2 on DSM 7.4.1, so it is listed for this model), signed in under one account, key expiry disabled for the NAS, and `tailscale set --advertise-routes=<nas-lan-ip>/32` run once with `sudo`, then approved in the admin console. The DSM package runs without root, so setting prefs needs `sudo` (or `--operator`) — the CLI refuses otherwise.
- **The result:** an iPhone on **5G with Wi-Fi off**, Tailscale connected, opened `https://nas.vandehaar.dev/` and received the gated page, a cookie, a `fetch()` with `200`, and an `<img>`. The private address is unreachable from cellular without the tunnel, so this route is what carried it. Same name, same certificate, same origin as at home, as designed.
- **Memory:** `tailscaled` sits at about **26–31 MB** resident with the NAS still showing about **210 MB available**, against the ~186 MB feared. The 512 MB box copes.

Still unmeasured, and carried on issue #56: video and range requests and throughput away from home, the overlap trap on a foreign network that uses the home's own address range (the home LAN is on a very common consumer range, so this matters), the split-DNS entry, VPN On Demand on the iPads, and Android at home.
